AI-Driven Adaptive Reading Assistance System for Dyslexic Users


Objectives
Primary objectives
1. Design and develop a browser-based intelligent reading assistance system that detects reading difficulty in real time without requiring clinical diagnosis or explicit user self-declaration.
2. Build an agentic AI pipeline that does not just flag difficulty but autonomously selects, applies, and refines reading interventions based on individual user behaviour across sessions.
3. Create a unified system that serves both dyslexic users (with profile-based, persistent adaptation) and general users (with passive, threshold-triggered assistance) within the same extension.
4. Ensure all behavioural data is processed locally on-device, making the system privacy-preserving by architecture rather than by policy.
5. Deliver measurable improvement in reading speed, comprehension accuracy, and cognitive fatigue for users with reading difficulty compared to an unaided baseline.
Secondary objectives
6. Build a graduated intervention taxonomy that moves from least intrusive (typography) to most intrusive (content rewriting) so the system never over-assists before trying lighter options.
7. Develop a personalisation layer that learns each user's intervention preferences and difficulty thresholds across sessions, making the system more precise over time.
8. Evaluate the system's accuracy in detecting reading difficulty against self-reported user ratings, and its efficacy in improving outcomes through controlled user studies.
9. Demonstrate that dyslexia-oriented design principles — larger spacing, dyslexia-optimised fonts, reduced visual crowding — benefit a broader population of struggling readers, not just those with a diagnosis.
10. Produce a system that is non-stigmatising, framing all assistance as a reading enhancement available to any user rather than a disability accommodation.


Workflow
Step 1 — Extension installation and onboarding
* User installs the Chrome extension from the Chrome Web Store.
* On first launch, a short onboarding screen presents three options: "I have dyslexia and want full assistance," "I sometimes struggle with reading and want smart help," or "Just watch and help me automatically."
* If the user selects the first option, they are taken through a brief preference setup — preferred font (OpenDyslexic, Lexie Readable, or system default), preferred background tint, whether they want text-to-speech enabled by default.
* If the user selects the second or third option, the system starts in passive mode with no visible changes applied yet.
* A user profile is created locally in chrome.storage.local with an initial difficulty score set by the onboarding choice (0.8 for declared dyslexia, 0.4 for self-reported occasional difficulty, 0.1 for fully automatic mode).
Step 2 — Page load and content extraction
* When the user navigates to any webpage, the content script fires immediately.
* The script scans the DOM and identifies readable text nodes — paragraphs, article bodies, headings — using tag and density heuristics to filter out navigation menus, footers, and ads.
* Each readable paragraph is tagged with a unique identifier and its word count is recorded.
* The script checks the user's profile to determine whether baseline adaptations should be applied immediately (dyslexia mode) or whether the page should be observed first (passive mode).
* If dyslexia mode is active, CSS adaptations are injected immediately: font is swapped, line height increased to 1.7x, letter spacing increased, background tint applied.
Step 3 — Behavioural signal collection
* IntersectionObserver is attached to every tagged paragraph, recording the exact timestamp when each paragraph enters and leaves the viewport.
* Scroll position is sampled every 100 milliseconds and stored in a rolling buffer; upward scroll movements exceeding 15% of viewport height within 3 seconds of a downward movement are flagged as regression events.
* Mouse hover events near word boundaries are recorded to approximate fixation duration on individual words.
* copy, contextmenu, and selectstart events are intercepted to count how often the user highlights or copies text.
* Any right-click → "search" or browser dictionary lookup is logged as a vocabulary difficulty event.
* All raw events are immediately converted to derived features and the raw data discarded — nothing sensitive is retained.
Step 4 — Feature computation
* After the user has been on the page for at least 30 seconds, the signal collector computes the following session features:
* Estimated reading speed in words per minute (total words in viewed paragraphs divided by total dwell time).
* Regression rate (number of regression events per 100 words read).
* Copy and lookup frequency (events per session).
* Paragraph completion rate (proportion of visible paragraphs where dwell time suggests full reading vs skimming).
* Vocabulary difficulty index (proportion of words in the page above the 5,000 most common English words, pre-computed from a bundled frequency list).
* These features are normalised against population baselines derived from published reading behaviour research and stored as a feature vector.
Step 5 — Difficulty scoring
* The feature vector is passed to the TensorFlow.js difficulty scorer running entirely in-browser.
* The scorer outputs a difficulty score between 0 and 1 for the current session.
* This session score is combined with the user's historical running average using an exponentially weighted moving average, giving more weight to recent sessions so the profile adapts as reading material changes.
* The updated score is written back to the local user profile.
Step 6 — Agent decision
* The agentic decision loop reads the updated difficulty score and the user's intervention history from the profile.
* It applies the following graduated decision logic:
* Score below 0.3 — no action, continue monitoring.
* Score between 0.3 and 0.5 — apply silent typography adaptations only (font, spacing, tint) without notifying the user.
* Score between 0.5 and 0.7 — surface a non-intrusive notification ("Reading seems harder on this page — want us to adjust it?") and offer structural changes (paragraph breaking, reading ruler) if accepted.
* Score above 0.7 — offer full assistance including content simplification and text-to-speech.
* If the user has previously dismissed an intervention at a given level, the agent does not re-offer that same level on the next page — it waits until the score rises further before escalating.
* If the user has previously accepted an intervention, the agent applies it silently on future pages without asking again.
Step 7 — Intervention execution
* Typography adaptations are executed by injecting a dynamically generated stylesheet into the page, targeting identified readable text nodes.
* Structural adaptations are executed by directly modifying the DOM — long paragraphs are split at sentence boundaries detected by the bundled tokeniser, and a reading ruler overlay is created as an absolutely positioned div that tracks scroll position via a scroll event listener.
* Content simplification is executed by sending the paragraph text to the backend proxy, which calls the LLM API with a structured prompt instructing it to simplify sentence structure, reduce vocabulary complexity, and preserve all factual content. The simplified text is returned and injected in place of the original, with an "original" toggle so the user can always switch back.
* Vocabulary support is executed by pre-screening the paragraph's words against the frequency list, identifying the top 5 most difficult words, and wrapping them in span elements with hover listeners that trigger a lightweight API call to fetch a plain-English definition displayed as a tooltip.
* Text-to-speech is executed using the browser's built-in SpeechSynthesis API with word-level highlight synchronisation achieved by splitting the paragraph into word tokens and advancing a CSS highlight class in sync with the speech timeline.
Step 8 — User feedback capture
* Every intervention generates a feedback event: accepted (user kept the change), dismissed (user clicked undo or closed the notification), or ignored (notification shown but neither accepted nor dismissed within 30 seconds, treated as a soft dismiss).
* Accepted interventions increase the weight of that intervention type in the user's profile for future sessions.
* Dismissed interventions lower the weight and raise the threshold at which that intervention is offered again.
* This feedback loop is implemented as a simple weighted preference store — no remote model training, no data leaving the device.
Step 9 — Cross-session learning
* On every subsequent page load, the profile manager loads the user's accumulated difficulty score, intervention preferences, and per-domain settings.
* Domains where the user consistently has high difficulty scores (academic databases, legal sites, medical content) get proactive adaptations applied from page load without waiting for the session scorer to run.
* Domains where the user consistently dismisses interventions (social media, casual news) are added to a low-sensitivity list where the threshold for triggering assistance is raised.
* Once per week, the profile computes a summary of the user's reading patterns and surfaces it in the extension popup — average reading speed, most difficult content types, which interventions were used most — giving the user transparency into what the system has learned about them.
Step 10 — User control and override
* At any point, the user can open the extension popup and see the current difficulty score, which adaptations are active, and the full profile summary.
* Individual adaptations can be toggled on or off independently.
* The entire system can be paused globally or per-domain with one click.
* The user can reset their profile entirely, returning the system to the onboarding state.
* A "why is this happening" button on every notification explains in plain language what signal triggered the intervention, giving full transparency into the agent's reasoning.


  



















Tech Stack:




Area
	Technology Chosen
	What It Is About
	Why This Is Better Than Others
	Extension
	Manifest V3
	The core Chrome extension framework that manages permissions, scripts, background services, and browser interaction.
	Official modern Chrome standard, better security, lower memory usage, faster performance, and required for Chrome Web Store publishing.
	Frontend
	React + TypeScript
	Builds the user interface such as popup screens, onboarding, dashboards, and settings.
	Component-based, scalable, huge ecosystem, easier debugging, and TypeScript adds safer code with fewer runtime errors.
	Styling
	Tailwind CSS
	Used for designing layouts, spacing, colors, fonts, and responsive UI.
	Faster UI development, clean styling, accessibility-friendly, lightweight, and easier to maintain than large CSS files.
	State Management
	Zustand
	Manages shared application data like user settings, difficulty score, and active interventions.
	Much simpler and lighter than Redux, minimal boilerplate, easy learning curve, and perfect for medium-sized projects.
	AI
	TensorFlow.js
	Runs machine learning models directly inside the browser for difficulty prediction.
	Fully browser-based, privacy-preserving, offline support, free, and avoids server-side AI costs.
	NLP
	compromise.js
	Performs natural language processing tasks like sentence splitting and word analysis.
	Lightweight, browser-friendly, fast, and easier to use compared to heavy NLP libraries like spaCy or transformers.
	Content Extraction
	Readability.js
	Extracts the main readable article content from webpages while removing ads and clutter.
	High-quality extraction, used in Firefox Reader Mode, lightweight, and reliable for articles and blogs.
	Storage
	chrome.storage.local
	Stores user preferences, reading history, and intervention settings locally in the browser.
	Built into Chrome, privacy-friendly, persistent storage, simple API, and no external database required.
	Backend
	Node.js + Express
	Handles API requests such as text simplification and optional cloud services.
	Same language as frontend (JavaScript), lightweight, beginner-friendly, fast API development, and huge ecosystem support.
	Simplification
	Gemini API
	Simplifies difficult text into easier-to-read language for dyslexic users.
	Strong text rewriting capability, generous free tier, fast response time, and easy API integration.
	Charts
	Chart.js
	Creates graphs and analytics visualizations for reading progress and user statistics.
	Lightweight, responsive, beginner-friendly, interactive, and ideal for browser extension dashboards.
	TTS
	SpeechSynthesis API
	Converts text into speech directly in the browser.
	Completely free, built into browsers, offline support, low latency, and no third-party API cost.

	What We Measure
	Why It Indicates Difficulty
	Scroll Backtrack
	User scrolls up after scrolling down in same paragraph

	Dwell Spike
	Cursor hovers over a word > 2× median dwell time
	Word is unfamiliar or visually confusing
	Re-read Loop
	Same 40px vertical band traversed 3+ times
	Paragraph comprehension failure
	Reading Pace Drop
	Words-per-minute (inferred from cursor) drops >40%
	Sudden complexity or visual fatigue
	Tab Abandon
	User switches tab and returns within 10s, repeated 2+ times
	Frustration / avoidance behaviour
	Selection Trace
	Text selected character-by-character (not word-click)
	Fine-motor tracking difficulty
	Gaze Divergence ᵒᵖᵗ
	Gaze (webcam) drifts away from active line

How to read this plan
* Each week has a single goal. If we hit it, we move on. If we don't, we cut scope from the next week, not from quality.
* "Joint" rows mean two or three devs sit together on the same task — usually for a shared contract or a bug bash.
* All shared types (UserProfile, FeatureVector, Intervention) live in one shared package. One source of truth.
* Daily 15-min standup. Friday 1-hour integration session. Decisions get logged with rationale.

Cross-cutting practices
* Shared types package — Honnashree, Saanvi, Manoj all import from one source of truth.
* Testing matrix — each dev maintains tests for their layer; joint E2E test on 5 canonical pages.
* Decision log — every threshold and weight choice gets a one-line rationale. We'll need it for the eval write-up.
* Friday integration session — 1 hour, fix what broke at the seams.


Critical path and risk hot-spots
1. Week 3 score calibration — if thresholds are off, every later week looks broken. Budget time to iterate.
2. Week 4 SPA and CSP issues — these surface late and eat days. Test a strict-CSP site (GitHub, Twitter) by mid Week 2.
3. Week 6 evaluation recruitment — start recruiting users in Week 5, not Week 6.


Buffer / cut list
There is no explicit buffer week. If we slip:
* First to drop: content simplification + TTS (push to v1.1). Tier 1 (typography) and Tier 2 (structural) still ship and cover the core thesis without the LLM dependency.
* Second to drop: ML scorer upgrade in Week 4 — keep the rule-based scorer.
* Do not drop: evaluation study. Without it we don't know if the system works.


Definition of done — v1
* Extension passes Chrome Web Store review.
* Onboarding works for all 3 modes.
* Detection produces a non-trivial score on at least 5 different content types.
* Tier 1 and Tier 2 interventions work on the 20 sites in the bug-bash list.
* Tier 3 (Gemini simplification + TTS) works on at least 3 site types.
* Evaluation report shows directional improvement in at least one of: reading speed, comprehension, perceived load.
* Profile data never leaves the device. Only paragraph text the user explicitly opts to simplify is sent to the backend.
